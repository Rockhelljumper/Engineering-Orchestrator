Command Center Wireframes

Low/mid-fidelity wireframes for deliverable 4 of the Engineering Orchestrator Command Center proposal (proposal.md, same folder). They show layout and data provenance, not visual design. All numbers, names and ids in the frames are placeholders. Each numbered pin is explained beside its frame, naming the record the panel is drawn from. Where no verified source exists, the panel shows "no data", never an estimate.

1 Portfolio overview 2 Project dashboard 3 AI Manager chat 4 Agent fleet 5 Execution inspector 6 Approval center

1. Portfolio overview

Every project in the workspace on one screen. Attention items (approvals, blockers, integrity) come first; activity second.

Data sources

  1. 1Needs you: pending approval.requested, open escalation.raised and integrity.alert events across projects, ordered by age. Each row links to the journal record.
  2. 2Project cards: counts of task states from the controller projection at the shown cursor. The "done / planned" bar is exactly that ratio, not an estimate of effort.
  3. 3Spend vs. cap: budget.settle (spent), open budget.reserve (reserved), caps from the project policy. Labelled as a client-side estimate (docs/07 §5).
  4. 4Activity: the workspace event stream. Controller events carry a journal chip; runner chatter is dashed and marked unverified.
  5. 5Metrics render only through the metric registry; below minSample the panel says so instead of drawing a line.
  6. ·Stream status (top right): live, reconnecting, or "resynced at cursor". Never hidden.

2. Project dashboard

One project: task DAG, board by lifecycle state, budget, blockers and the controller's health.

Data sources

  1. 1Task graph: tasks and deps from the store snapshot (src/store/types.ts), colour = state from task.transitioned. Layout via ELK; nodes animate only when a transition event arrives.
  2. 2Board: the same projection grouped by the states in src/states.ts; attempt and counters from TaskCounters.
  3. 3Budget: budget.reserve/budget.settle records and caps from policy.json (src/budget.ts, src/policy.ts).
  4. 4Blocker: the escalation record (EscalationRecord in src/controller.ts). "Request unblock" submits an intent that creates an approval; it does not change state.
  5. 5Health: eo doctor report and anchor inspection (src/doctor.ts, src/anchor.ts); tier from the run record.
  6. ·Run ▸ sends run.start; the button shows "submitted" until run.started arrives.

3. AI Manager chat

Conversation with a persistent manager. The manager proposes intents as cards; the human confirms; the controller decides.

Data sources

  1. 1Messages: conversation.message_posted from the workspace store (hash-chained). Manager text is the agent's claim; facts in it must carry citation chips that resolve.
  2. 2Intent card: the manager's structured proposedIntents[]. "Submit" posts an intent; status moves only on intent.accepted/intent.rejected.
  3. 3Context: the retrieval log of this manager run (journal refs, evidence, accepted memory). Quarantined memory never appears.
  4. 4Permissions: effective capabilities computed by the controller for the manager's run token, not the agent's self-description.
  5. 5Cost: the manager run's budget.settle; until a live runner exists the panel says why it is empty.

4. Agent fleet

All agent instances across projects: definition version, model route, permissions, assignments and current activity.

Data sources

  1. 1Instances: the agent registry (workspace store) joined with run records; "running T5" means an open run whose attempt.start has no attempt.end yet.
  2. 2Effective tools: computed by the controller from the definition, project policy, pinned skills and token; the same function the runner uses, so the view cannot drift from enforcement.
  3. 3Route: route table version and its eval report artifact (stored evidence). The diversity rule is shown when policy requires it.
  4. 4Live activity: agent.activity from the runner stream, styled as an unverified claim. "all tests pass" here counts for nothing.
  5. 5Reliability: registered metrics over attempt.end and transitions; metrics that need verifier data say which milestone provides it.

5. Execution inspector

One task attempt end to end: journal timeline, gate results by clause, evidence files with hashes, logs and the replay command.

Data sources

  1. 1Timeline: every journal record with this task and attempt (budget.*, task.transition, attempt.end, evidence.sealed), seq shown; runner spans collapsed and marked unverified. Grouped by correlationId.
  2. 2Gates: gate.evaluated from the M3 gate engine, one row per Definition-of-Done clause (docs/02 §6). Before M3 the panel shows "no gate engine yet".
  3. 3Manifest: evidence/<task>/<attempt>/manifest.json (src/evidence.ts); the MAC is re-checked by the controller on every read.
  4. 4Logs: evidence files streamed through the controller read API, never read from a worker clone.
  5. 5Report: the agent's summary from attempt.end, rendered in the claim style.
  6. ·Replay: the recorded eo verify --task T3 --replay command (M3-6).

6. Approval center

Every human decision across projects. Each decision is bound to a subject hash and needs a fresh passkey check; console-only operations are listed with their command.

Data sources

  1. 1Queue: approval.requested without approval.decided/approval.expired, across projects the viewer can read. Expiry comes from the approval record.
  2. 2Console only: operations the API cannot perform (policy edits, repository approval, anchor adoption), shown with the exact eo command (src/cli.ts).
  3. 3Detail: subject hash (for a plan, planHash in src/plan.ts), requester principal, reservation estimate from the budget rules, and the plan diff. The manager's rationale is a claim.
  4. 4Decision: requires a WebAuthn step-up ≤ 5 min old; the controller verifies the assertion and that the subject hash is unchanged, then journals approval.decided. Agents can never reach this control.
  5. 5Audit: decided approvals with actor and channel (web or console); TTY approvals appear here too.
